# Судебный парсер — рабочее ТЗ (черновик)

> **Обновление 13.11.2026:** цель уточнена — парсер нужен для **анализа судебной практики**
> (исходы, статьи, суммы по спорам с участием ОСИ). Эта часть сделана, см. [PRACTICE.md](PRACTICE.md)
> и раздел «Анализ судебной практики» в README. Ниже — исходные допущения для части «мониторинг должников».

Полного технического задания нет, поэтому ниже — мои допущения.
Их нужно согласовать с Виталием; всё, что он поправит, меняется в коде без переписывания.

## 1. Цель

Автоматически находить судебные дела по должникам ОСИ (жильцам, которые не платят
за содержание дома) и показывать, на какой стадии каждое дело.
Это продолжает функцию «Оплата и долги» в приложении e-KNOT.

## 2. Вход

CSV- или Excel-файл со списком должников:

| Поле      | Обязательно | Пример               |
|-----------|-------------|----------------------|
| iin       | да*         | 900101300123         |
| full_name | да*         | Иванов Иван Иванович |
| osi_bin   | нет         | 210140012347         |
| apartment | нет         | 45                   |
| debt_kzt  | нет         | 150000               |

\* нужен хотя бы один из `iin` / `full_name`. Поиск по ИИН — основной, по ФИО — запасной
(с пометкой «нужна проверка», так как возможны однофамильцы).

## 3. Выход

1. **База SQLite** (`data/cases.db`) — все найденные дела, история изменений статусов.
2. **Excel-отчёт** — одна строка на дело:
   ИИН, ФИО, номер дела, суд, категория, стороны, сумма, статус, дата, ссылка, дата проверки.
3. **Список изменений** с прошлого запуска: новые дела, сменившийся статус.

## 4. Источники данных

| Источник                | Что даёт                          | Очередь |
|-------------------------|-----------------------------------|---------|
| portal-sot.kz (график)  | назначенные заседания — **подключён** | 1   |
| portal-sot.kz (вход по ЭЦП) | статусы дел, судебные акты    | 2       |
| aisoip.adilet.gov.kz    | исполнительные производства (закрыт капчей) | 3 |

Каждый источник — отдельный модуль; добавление нового не трогает остальной код.

## 5. Режимы работы

- **Разовый прогон** — по файлу получить отчёт.
- **Регулярный мониторинг** — запуск по расписанию (например, раз в сутки), в отчёт попадает только новое.

## 6. Нефункциональные требования

- **Бережность к сайту суда**: пауза между запросами (по умолчанию 2 с), не более 1 потока на источник.
- **Надёжность**: повтор запроса при сетевой ошибке (до 3 раз с растущей паузой); падение на одном
  должнике не останавливает весь прогон.
- **Без дублей**: дело однозначно определяется парой (источник, номер дела).
- **Логи**: каждый запуск пишет журнал — сколько обработано, найдено, ошибок.
- **Законность**: только открытые данные; капчи и защиту от ботов не обходим. Если источник
  требует ЭЦП или капчу — нужен официальный доступ от компании.
- **Персональные данные**: ИИН и ФИО не попадают в репозиторий, логи и публичные места.

## 7. Масштабирование (следующие шаги)

- PostgreSQL вместо SQLite.
- Очередь задач (например, Celery/RQ) и несколько воркеров с общим ограничением скорости.
- REST API (FastAPI), чтобы приложение e-KNOT получало статусы дел напрямую.
- Уведомления председателю ОСИ о новых делах / решениях.
